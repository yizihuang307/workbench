# 个人工作台：产品设计规范与流程基线

用途：作为后续模块需求分析、交互设计、开发、测试和发布的共同基线。

## 一、产品设计原则

1. 核心内容优先：首屏优先正文、列表和主要操作，非正文内容不得挤占主要空间。
2. 清晰胜过装饰：必要文字不能使用过小字号、过浅灰色或含义不明的图标。
3. 保持有效信息密度：减少无意义留白，让一屏展示足够内容但不拥挤。
4. 简单优先：不提前增加没有明确价值的字段、配置、层级和框架。
5. 操作状态稳定：操作前后不位移、不跳动，不丢滚动和焦点。
6. 高频操作可逆：低风险操作直接执行；删除采用“立即删除＋5秒撤销”。
7. 区分桌面和手机：桌面可拖拽，手机必须有可靠替代操作。
8. 先确定规则再开发：开发前明确字段、状态、异常、边界和发布门槛。

## 二、全局导航规范

- 桌面端使用钴蓝底白字左侧目录栏，宽度参考 `176px`，选中状态清晰克制。
- 手机端使用蓝底白字底部导航。
- 未开发入口统一隐藏或显示“即将开放”，不得保留死入口。

## 三、页面布局规范

- 顶部标题、问候和状态尽量合并；大字标语优先单行，小屏自然换行但不得横向滚动。
- 删除无决策价值的重复信息；正文尽早进入首屏；非正文区域不得压缩主要列表。

## 四、字体与视觉规范

- 全站使用统一无衬线字体栈；正文和事项标题必须易读。
- 同层级字号、字重和行高一致；超长文字不得撑破卡片或遮挡按钮。
- 页面缩放至 200% 仍可操作。
- 图标使用稳定矢量或组件图标，不依赖字符字体。
- 仅图标按钮必须有可访问名称和悬停提示；点击热区原则上不小于 `44×44px`。
- 快速记录按钮必须融入整体视觉体系。

## 五、列表规范

- 以一屏展示足够事项为目标；勾选框、标题、标签、操作按钮保持同一基线。
- 勾选前后预留相同空间；行内标签紧跟文字；行尾操作紧凑但热区足够。
- 超长标题换行或截断，不挤压操作按钮。

## 六、全局交互规范

### 操作菜单

- 点击空白处或按 `Esc` 关闭；打开新菜单自动关闭旧菜单。
- 菜单只保留不能直接完成的操作；桌面已有拖拽时不提供上移/下移。
- 手机端替代排序能力按模块确认。

### 弹层和放大视图

- 集中处理区域优先中央大弹层，和原页面操作同一份数据。
- 支持关闭按钮、遮罩、`Esc`；禁止背景误滚动；焦点限制在弹层内。
- 关闭后焦点返回触发按钮并保留滚动位置。

### 拖拽

- 桌面端支持排序和跨区域移动；覆盖空列表、长列表末尾、滚动容器、取消拖拽和隐藏项目。
- 手机端不能只依赖拖拽；跨区移动落点必须明确。

## 七、数据设计规范

内部保留唯一 ID、所属区域或状态、排序值、创建和更新时间、完成状态、数据版本及迁移兼容字段。界面字段少不代表可以省略稳定性字段。

### 本地版边界

- 无账号阶段使用浏览器本地存储，刷新、关闭、重启后可恢复。
- 处理多标签页同步、旧版本、损坏数据和容量不足。
- 不宣称支持跨设备、多用户或正式协作。

### 正式在线版边界

必须补齐账号认证、服务端持久化、权限隔离、接口失败、并发冲突、安全权限测试和跨设备同步测试。

## 八、技术架构基线

| 层级 | 技术方案 | 职责 |
|---|---|---|
| 前端 | React＋TypeScript | 页面、交互、状态和响应式 |
| 样式组件 | Tailwind CSS，参考 shadcn/ui | 统一视觉和可访问性 |
| 后端 API | Hono＋TypeScript | 复杂业务、权限、批量操作和审计 |
| 数据库 | Supabase PostgreSQL | 持久化业务数据 |
| 认证 | Supabase Auth | 首期邮箱密码，后续企业 SSO |
| 权限 | Supabase RLS | 用户数据隔离 |
| 运行环境 | 优先 Supabase Edge Functions | 承载 Hono API |
| 构建发布 | Sites | 构建、预览和发布，不属于业务框架 |

简单 CRUD 可评估前端直连 Supabase；批量修改、审计、复杂权限和关键规则统一经过 Hono。

## 九、【安排】模块局部规则

- 首页分等宽的今日安排与后续安排两个区域；原本周安排并入后续安排。区域内滚动，不展开收起；每区支持中央放大视图。
- 可见字段为标题、最优先及可选预计完成日期；今日允许多个最优先，标签紧跟标题并使用星形图标。预计完成日期未填写时不显示占位内容。
- 完成和恢复不改变位置；隐藏已完成为全局开关。
- 桌面直接拖拽；菜单不提供上移和下移；删除后提供5秒撤销。
- 新增事项沿用现有置顶输入框交互与样式，不新增弹层、按钮样式或其他录入入口。
- 后续安排提供下拉筛选，选项为全部（默认）、本周、下周、本月；未填写预计完成日期的事项仅在“全部”中展示。
- 仅未完成的后续事项在预计完成日期到达时移入今日安排；若用户未在当天打开首页，则下次打开时补做迁移并标记“已逾期”。从后续安排逾期迁入的事项展示紧凑标签“已逾期 · M/D”，保留原计划日期；今日安排中无预计完成日期的跨日未完成事项仅标记“已逾期”，不伪造原计划日期。已逾期标签完全复用原“昨日遗留”标签样式，仅替换文案；不再使用“昨日遗留”或“本周遗留”。
- 已完成的后续事项不因预计完成日期到达或超期而移动；其展示与隐藏继续遵循全局隐藏已完成规则，完成当天可见、次日自动隐藏。
- 完成记录不显示事项曾来自今日或后续安排；有预计完成日期的事项仅显示原计划日期。
- 后续安排模块沿用原本周安排的背景色；两个模块使用等宽布局，其余现有视觉样式不调整。
- 标题最多200字，去除首尾空格，纯空格不能保存，允许同名。

这些规则只属于【安排】，后续模块复用方法，不复制具体结构。

## 十、下一模块标准设计流程

### 阶段A：定义目标

确定核心问题、场景、成功标准、交付等级和明确不做项；输出一句目标、3～5条可验证标准及范围清单。

### 阶段B：梳理对象与状态

依次确定场景、业务对象、最少字段、生命周期、状态进入/退出/恢复、空与异常状态、极端数据量和权限边界。

### 阶段C：集中确认决策

- 独立问题集中确认，依赖问题顺序确认；每题提供2～3个互斥选项并说明推荐取舍。
- 用户修改答案时以最后明确表达为准；记录分“已确认／待确认／后续阶段”。

### 阶段D：冻结功能边界

开发前确定新增、查看、编辑、删除、恢复、排序、移动、搜索、筛选、端差异、保存同步冲突失败、未开发入口、键盘可访问性和响应式边界。

### 阶段E：先写测试再开发

| 类别 | 必须覆盖 |
|---|---|
| 正常链路 | 首次进入、核心任务、刷新恢复 |
| 输入边界 | 空值、空格、超长、多语言、特殊字符、输入法 |
| 状态边界 | 重复点击、撤销、恢复、切换、操作中关闭 |
| 数量边界 | 空、1条、长列表、1000条或合理上限 |
| 布局边界 | 320px、平板、桌面、超长文案、200%缩放 |
| 数据异常 | 损坏、旧版本、容量不足、断网、多标签页 |
| 安全 | 文本注入、越权、敏感信息暴露 |
| 可访问性 | 键盘、焦点、对比度、热区、减少动画 |
| 性能 | 长列表滚动、频繁操作、弹层开关 |

正式在线版增加登录失败、会话过期、RLS隔离、接口超时重试、并发冲突、幂等和审计。

### 阶段F：开发与验证

只实现冻结范围；通过静态检查、自动测试和构建；真实页面验证桌面与手机；人工检查字号、对比度、跳动、焦点、菜单关闭、拖拽落点和滚动；逐项验收 P0，不能以构建成功代替产品验收。

### 阶段G：反馈闭环

反馈采用“区域＋问题＋期望”；修改前明确验收标准；只改直接相关内容；验证原问题和回归点；发布说明分已完成、已验证、仍未完成。

## 十一、发布门槛

- 所有 P0 测试通过；无数据丢失、误删、错位、崩溃或死按钮。
- 桌面和手机核心链路经过真实页面验证；菜单、弹层正常退出；无焦点陷阱和意外跳动。
- 长列表操作流畅；刷新、断网、异常存储、多标签页有明确结果；控制台无阻塞错误。
- 自动测试和构建通过；未实现的账号、同步、权限和后端能力明确标注。

## 十二、特别注意事项

1. 不把【安排】局部规则当作全产品规范。
2. 不因页面看似完成而跳过异常、移动端和数据测试。
3. 不把 Sites 描述成前端或后端框架。
4. 不提前搭建没有真实调用的 Hono 服务。
5. 不使用字符字体渲染关键图标。
6. 不使用过小浅灰字承载必要信息。
7. 不保留无法退出的菜单或弹层。
8. 不用自动测试代替桌面和手机真实验收。
9. 不默默改变已确认规则。
10. 不增加无法追溯到本轮需求的功能。
