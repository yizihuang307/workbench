# 安排模块改造：开发、数据迁移与上线规范

> 状态：已确认，可直接实施。  
> 目标：在不扩展为日程表的前提下，将首页的“本周安排”和“后续安排”合并为“后续安排”，增加可选预计完成日期、有限日期筛选及未完成事项到期迁移。

## 1. 范围与明确不做

### 本次必须实现

1. 首页只保留等宽的【今日安排】和【后续安排】两个模块。
2. 【本周安排】并入【后续安排】；后续安排沿用原本周安排背景色。
3. 后续事项支持可选的预计完成日期；已填写才展示日期，未填写不显示占位。
4. 后续安排下拉筛选：`全部`（默认）、`本周`、`下周`、`本月`。
5. 仅未完成事项按预计完成日期自动移入今日安排；逾期时标记【已逾期】。
6. 后续安排支持与今日安排完全相同的 P0 星标设置。
7. 完成记录移除“来自今日／来自本周／来自后续”等来源字段与文案。

### 本次明确不做

- 小时级日程、周/月日历、重复事项、提醒通知、会议邀请、共享协作。
- 自由拖拽调整模块尺寸或任意栅格布局。
- 新增事项的新弹层或新录入入口。
- 修改现有完成、恢复、删除、撤销、拖拽排序、隐藏已完成的基本交互。

## 2. 冻结后的产品规则

### 2.1 模块与视觉

- 桌面端两个模块等宽并列；移动端依次显示今日安排、后续安排，均为全宽。
- 新增事项继续使用每个模块内现有的置顶输入框，交互和视觉不改变。
- 后续安排复用原【本周安排】背景色。
- 【已逾期】必须完全复用现有【昨日遗留】标签的颜色、字号、内边距和圆角，仅替换文案。
- P0 是事项属性，在今日与后续都可设置、取消；完成后 P0 保留；不得因 P0 自动改变排序。

### 2.2 预计完成日期

- 字段为可选的纯日期（`YYYY-MM-DD`），不含时间。
- 后续事项行内可选择、修改或清除日期；未设置时不显示占位文字。
- 已设置日期在行尾紧凑显示；标题过长时标题优先截断，日期不可换行。
- 用户把日期选为今天：保存后立即移入今日安排。
- 用户把日期选为过去：保存后立即移入今日安排并标记【已逾期】。
- 用户将已迁入今日的事项日期改为未来：移回后续安排并清除逾期状态。

### 2.3 后续安排筛选

| 选项 | 结果 |
|---|---|
| 全部（默认） | 所有后续事项；未设置日期的事项也在此显示 |
| 本周 | 本周一至周日内、已设置日期的事项 |
| 下周 | 下一个周一至周日内、已设置日期的事项 |
| 本月 | 当前自然月内、已设置日期的事项 |

- 日期范围按用户 `profiles.timezone` 计算，缺省为 `Asia/Shanghai`。
- 筛选仅影响展示，不改变排序或数据。
- 已完成事项继续使用既有规则：完成当天可见、次日自动隐藏；全局“隐藏已完成”开关仍可立即隐藏。

### 2.4 到期、逾期与完成

- 仅 `is_completed = false` 的事项参与自动移动；已完成事项绝不因日期到达或超期而移动、也不标记逾期。
- 后续事项 `expected_completion_date = 今天`：读取首页或任务列表时，原子地移动到 `area=today`。
- 后续事项日期早于今天：下次读取首页或任务列表时，原子地移动到今日并标记 `is_overdue=true`。
- 今日事项未完成且已跨日：保留在今日并标记 `is_overdue=true`。
- 从后续安排逾期迁入的事项显示 `已逾期 · M/D`；今日中原本未设日期而跨日的事项仅显示 `已逾期`，不得虚构原计划日期。
- 不再使用“昨日遗留”“本周遗留”“上周遗留”及 `is_legacy`。

### 2.5 完成记录

- 完成记录只显示事项标题、完成时间，以及有值时的“原计划 M/D”。
- 移除 `source` 的持久化、类型、接口返回和 UI 文案。
- 恢复为未完成时，仍按现有规则从完成记录移除。

## 3. 数据模型与迁移

### 3.1 目标 `tasks` 字段

```sql
area text not null check (area in ('today', 'later')),
expected_completion_date date null,
is_overdue boolean not null default false
```

保留：`id, user_id, title, is_completed, is_p0, sort_key, completed_at, version, created_at, updated_at, deleted_at`。

删除：`is_legacy`。

### 3.2 迁移顺序（单个 SQL migration，事务内）

1. 添加 `expected_completion_date date null` 和 `is_overdue boolean not null default false`。
2. 将历史 `area='week'` 更新为 `area='later'`；**不得**猜测或填充预计完成日期。
3. 将所有历史 `is_legacy` 信息丢弃；迁移后由新规则重新计算 `is_overdue`。
4. 更新 `area` 的 check constraint，仅允许 `today/later`。
5. 删除 `is_legacy` 列。
6. 新建索引：

```sql
create index idx_tasks_later_due
  on tasks (user_id, area, expected_completion_date, sort_key)
  where deleted_at is null;
```

7. 保留既有 `idx_tasks_completed`；执行迁移后验证历史事项总数、完成数和 P0 数量不变。

迁移必须可安全重复执行（列、索引与约束使用存在性检查）；正式环境先备份数据库，再在 staging 做实际数据演练。

## 4. 后端与同步改造

### 4.1 类型与校验

- `TaskArea` 改为 `"today" | "later"`。
- `Task` 增加 `expectedCompletionDate: string | null`、`isOverdue: boolean`；删除 `isLegacy`。
- 新建/更新任务 DTO 接受可空 `expectedCompletionDate`，严格校验 ISO 日期；`area` 只接受 today/later。
- 完成记录 DTO 删除 `source`。

### 4.2 统一 rollover 函数

实现一个服务端函数（可命名 `rolloverDueTasks`），由 **`GET /api/tasks`** 和 **`GET /api/workbench-state`** 共同调用，禁止复制两套规则。

伪代码：

```text
today = current calendar date in profile timezone
for each non-deleted, incomplete task of current user:
  if area=later and expected_date <= today:
    update area=today, is_overdue=(expected_date < today), version=version+1
  else if area=today and (expected_date < today or (expected_date is null and created date < today)):
    update is_overdue=true, version=version+1
```

- 使用事务/RPC 或带版本条件的更新，保证重复读取幂等。
- 任何单条迁移失败不得导致其他事项重复迁移；读取失败需返回可识别错误，不能静默吞掉并返回不一致数据。
- 保存整页 workbench state 时，必须兼容旧客户端上传的 `week` 数组：服务端将其合并到 `later`，不丢数据；新客户端不再写入 `week`。

### 4.3 任务 API

- `GET /api/tasks?area=later&period=all|this-week|next-week|this-month`；缺省 `period=all`。
- 过滤范围由服务端按用户时区计算；未设日期仅在 all 返回。
- `POST /api/tasks` 与 `PATCH /api/tasks/:id` 支持日期字段。
- 修改日期为今天/过去时，可在 PATCH 事务内立即执行迁移，返回最终 `area/is_overdue`。
- 完成/恢复时不得自动重写预计完成日期；恢复后若日期已到/已过，下一次 rollover 应重新按规则处理。

## 5. 前端改造

1. 移除本周模块及所有 `week` 目标（包含拖拽、展开视图、菜单移动项、统计和文案）。
2. 首页 `board` 改为两个等宽区域；后续模块使用原 `.area-week` 背景样式。
3. 后续模块标题栏加入原生/现有风格下拉框，默认“全部”。不引入新组件库或自定义弹窗。
4. 后续行增加日期选择操作；日期展示右对齐；P0 星标按钮与今日使用同一组件和行为。
5. 今日行中的 `isOverdue` 使用原遗留标签样式与新文案；有预计日期时显示 `已逾期 · M/D`。
6. 完成记录删除来源标签；有预计日期时显示原计划日期。
7. 现有拖拽跨区到后续安排时保留 P0；不要再因移出今日自动取消 P0。

## 6. 必须新增或更新的测试

### 单元

- 时区边界：北京时间/用户时区的今日、本周、下周、本月范围。
- 无日期事项只出现在全部；四种筛选互斥且边界正确。
- 未完成后续事项：今天、过去、未来日期的迁移与逾期结果。
- 已完成后续事项：今天或过去日期均不迁移、不逾期。
- 今日无日期事项跨日标记逾期；有未来日期的今日事项不逾期。
- 完成当天可见、次日自动隐藏与全局隐藏开关。
- 旧 `week` 状态迁移到 `later` 不丢失任务、完成状态、P0、排序。

### 接口/数据库

- 数据迁移后的约束、索引、RLS、回滚预案验证。
- `GET /api/tasks` 与 `GET /api/workbench-state` 对同一数据返回一致的 area/overdue 状态。
- 并发读取 rollover 幂等，不产生重复或版本冲突。
- 日期非法、跨用户 PATCH、旧客户端含 week payload 均有预期结果。

### E2E

- 新建后续事项 → 设置今天/过去/未来日期 → 刷新 → 位置与标签正确。
- 后续筛选四选项、P0 切换、拖拽、完成/恢复、隐藏已完成。
- 完成记录无来源文案，有日期时显示原计划日期。
- 桌面两列等宽、移动端单列；新增输入框、已逾期标签、后续背景色均与旧样式一致。

## 7. 上线门槛与发布步骤

1. 在 staging 备份生产快照并执行迁移演练，核对任务总数、完成数、P0 数量、软删除数全部一致。
2. 合并后运行：类型检查、lint、单元/接口/E2E、生产构建；全部通过才允许发布。
3. 先发布数据库 migration，再发布后端，再发布前端；发布期间保留旧客户端 payload 兼容至少一个版本。
4. 发布后观察：任务读取错误率、rollover 更新失败、任务数异常下降、日期筛选空结果异常。
5. 若出现数据丢失、跨用户读取、重复迁移或完成事项被迁移，立即停止发布并按备份/回滚预案恢复。

## 8. 最终验收清单

- [ ] 首页无“本周安排”与“遗留”旧文案。
- [ ] 两个模块等宽；后续背景色等同旧本周模块；新增输入框未改变。
- [ ] 后续有 P0、日期和四项筛选；无日期不显示占位。
- [ ] 仅未完成事项到期/逾期迁入今日；已完成事项不移动。
- [ ] 今日跨日未完成正确显示“已逾期”。
- [ ] 完成记录不含来源信息，原计划日期正确。
- [ ] 迁移后无任务丢失，权限与跨设备同步正常。
- [ ] 自动化测试、生产构建和 staging 验收全部通过。
